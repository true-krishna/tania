# Phase 0 — Research: Masuk Single Sign-On (SSO) Microsoft Entra ID

**Feature**: `006-entra-sso-login` (TAN-267, plan untuk TAN-269) · **Date**: 2026-10-20

Audit 2026-10-20 atas `tania-dashboard` (branch `agent/diggie/8ed77434a094`, tracking `agent/cobra/ef1a3eb3f6ce`) dan `tania-backend` (branch sama). Fakta kode yang dipakai: jalur login existing = mutation GraphQL `login` → `AuthService.Login` (`internal/usecase/auth.go`) → `issueSession` (access JWT HS256 dari `internal/auth/token.go` + refresh token rotasi, hash SHA-256); rate limit memakai `RateLimiter.Allow` Redis dengan kunci `login:<clientKey>`; jejak audit existing menulis `outcome`/`reason` untuk penolakan; modul provisi Entra (`EntraService` + `platform/entra/graph.go`) memakai **client credentials** terhadap Graph dan **tidak** menyediakan alur login; migrasi `0002_core_model.sql` sudah menambahkan `users.auth_provider`, `users.entra_object_id`, `users.saml_name_id` — **ketiganya belum pernah dibaca/ditulis** kode mana pun. Tidak ada `NEEDS CLARIFICATION` tersisa; **seluruh butir yang menunggu keputusan pemilik produk diputuskan pada 2026-10-20** (FR-004 direvisi menjadi dua jalur pemetaan; opsi A untuk auto-redirect) — hasilnya tercatat di `plan.md` (D5, D5b, D8) dan pada baris `**Revisi**` spec. Sisa pekerjaan yang **bukan** milik fitur ini dirangkum di `plan.md` Open Item 6.

## R-1 — Alur autentikasi mana yang dipakai? (FR-001/FR-003)

- **Decision**: **OAuth 2.0 Authorization Code + PKCE** dengan `tania-backend` sebagai *confidential client*; bukti autentikasi yang divalidasi adalah **ID token** (bukan access token) (D1).
- **Rationale**: FR-003 mensyaratkan keabsahan bukti diverifikasi sebelum sesi terbentuk. Authorization Code menahan klaim di balik satu tukar-permintaan server yang bisa diverifikasi penuh (tanda tangan + `iss`/`aud`/`tid`/`nonce`), sedangkan implicit/hybrid menaruh token di URL (terlihat di log/proksi/riwayat, tanpa `nonce` yang terikat) dan sudah dideprecate oleh praktik industri. PKCE (`code_verifier`/`code_challenge`) mengikat `code` ke proses yang memintanya sehingga kode hasil rekayasa kembali tidak dapat ditukar oleh klien lain; didukung penuh untuk confidential client pada endpoint v2.0 tenant.
- **Alternatives considered**: (a) *implicit flow* / token di hash — ditolak (bukti tidak dapat diikat, token terekspos di sisi klien); (b) *client-side only* (browser menukar kode dengan `client_secret` di env `NEXT_PUBLIC_*`) — ditolak **fatal**: `NEXT_PUBLIC_*` dikompilasi ke browser, sehingga `CLIENT_SECRET` bocor ke publik (melanggar FR-010 & Security III); (c) *client-side only lalu verifikasi lewat `GET /me`* — ditolak: keputusan penerimaan berpindah ke browser (Technical VII) dan menambah panggilan jaringan tanpa mengurangi apa pun.

## R-2 — Siapa yang menutup alur: mutation GraphQL backend vs endpoint HTTP backend-hosted?

- **Decision**: mutation GraphQL publik **`loginWithEntra`** di `tania-backend` (D2). `/login/callback` adalah halaman frontend biasa yang membaca query string, lalu memanggil mutation itu.
- **Rationale**: seluruh kontrak autentikasi Tania hari ini (`login`, `refreshSession`, `logout`) berupa mutation GraphQL yang mengembalikan `AuthPayload`; `route-gate` (`src/lib/auth/route-gate.ts`) sudah menandai `/login*` sebagai rute publik, sehingga `/login/callback` tidak butuh perubahan sama sekali. Menambah `GET /auth/entra/callback` + `Set-Cookie` berarti **model sesi kedua** (cookie HttpOnly vs Bearer yang dipakai Apollo), dan menimbulkan duplikasi CORS/CSRF/perbedaan umur sesi — permukaan baru tanpa kebutuhan fungsi (Technical I/VII).
- **Alternatives considered**: (a) endpoint callback backend ber-set-cookie — ditolak (model sesi kedua, duplikasi kode sesi); (b) Next.js Server Action — ditolak (jalur server-to-server di luar kontrak GraphQL, tidak ada preseden di repo); (c) mutation yang menerima **ID token** saja tanpa pertukaran kode — ditolak: `id_token` tanpa pertukaran kode tidak punya sumber kebenaran klaim yang diikat PKCE dan menambah jalur penerimaan kedua yang harus diverifikasi.

## R-3 — Bagaimana keabsahan bukti divalidasi tanpa dependensi baru? (FR-003)

- **Decision**: `internal/platform/entra/oidc.go` menukar kode ke `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token`, lalu memverifikasi `id_token`: ambil **JWKS** dari `https://login.microsoftonline.com/{tenant}/discovery/v2.0/keys` (di-cache; refresh **sekali** bila `kid` tidak dikenal), petakan JWK → `rsa.PublicKey` dengan `math/big` + `crypto/rsa` (stdlib), verifikasi RS256 memakai **`github.com/golang-jwt/jwt/v5` yang sudah ada** di `go.mod`.
- **Rationale**: konstitusi Technical V menuntut dependency minimal; kebutuhan ini nyata-nyata terpenuhi oleh kombinasi stdlib + JWT library yang sudah terpasang untuk access token. JWKS adalah **kunci publik** — meng-cache-nya tidak perlu mengurangi keamanan; refresh-on-unknown-`kid` menangani rotasi kunci Microsoft tanpa restart proses.
- **Alternatives considered**: (a) library JWKS/OIDC pihak ketiga (ditolak — dependensi baru untuk parser JSON + RSA yang ~100 baris; wajib dicantumkan di MR); (b) selalu mengambil JWKS per permintaan (ditolak — tambahan latensi + gagal bila endpoint JWKS sedang lambat, tanpa keamanan tambahan); (c) tidak memverifikasi tanda tangan karena "dipercaya HTTPS" (ditolak — bukan validasi FR-003, mudah melewati `aud`/`tid`).

## R-4 — Bagaimana kebijakan single-tenant (NC-01) ditegakkan?

- **Decision**: tiga klaim dicek **sebelum** sesi apa pun terbentuk: `tid == ENTRA_TENANT_ID`, `iss == https://login.microsoftonline.com/{tid}/v2.0`, `aud == ENTRA_CLIENT_ID`, plus `exp`/`iat` dengan toleransi skew ≤5 menit dan kecocokan `nonce` (D4). Tidak ada **domain allow-list tambahan** (keputusan pemilik produk: semua akun dalam tenant boleh mencoba masuk).
- **Rationale**: menutup FR-005 (akun personal Microsoft / tenant lain ditolak) secara struktural — akun personal `outlook.com` tidak akan pernah punya `tid` == tenant Telkom, dan token dengan `aud` aplikasi lain ditolak. Mengecek `tid` terhadap konfigurasi tunggal jauh lebih sederhana dan lebih kuat daripada kecocokan domain nama, yang mudah salah (UPN tidak selalu sama dengan domain korporat, mis. hasil provisi FR-45).
- **Alternatives considered**: allow-list domain pada klaim email (ditolak — bukan single-tenant, rumit & tidak benar-benar menjamin milik tenant); konfirmasi tambahan lewat Graph `/me` (ditolak — panggilan jaringan tambahan per login tanpa mengubah keputusan, dan menambah kegagalan penuh bila Graph lambat).

## R-5 — Bagaimana identitas korporat dipetakan ke akun Tania? (NC-02, FR-004, FR-011)

- **Decision**: berurutan, berhenti pada kecocokan pertama (**D5**, sesuai FR-004 hasil revisi): **(1)** `oid` klaim → `users.entra_object_id` (keterkaitan mapan — jalur tercepat & stabil); **(2)** `oid` → `entra_provisions.object_id` → `employee_id` → `employees.user_id` → akun Tania (menutup akun hasil provisi CREATE); **(3)** `lower(users.email) = lower(klaim email/UPN)` → bila cocok dan `entra_object_id` masih NULL, **kaitkan sekali** (isi kolom). Bila (1) menemukan `oid` **berbeda** → **tolak**. Bila tidak cocok pada ketiganya → tolak **tanpa membuat akun**. Akun tidak `Active()` → tolak. Semua kegagalan memakai **satu pesan generik** (D11).
- **Rationale**: `oid` adalah identitas tenant yang stabil sementara email/UPN **bisa berubah** (edge case spec melarang perpindahan keterkaitan otomatis); menguji `oid`-dulu membuat perubahan email tidak berpengaruh setelah keterkaitan terbentuk. Langkah (2) ada karena FR-004 direvisi 2026-10-20: provisi CREATE menghasilkan **UPN turunan nama** (`rina.kusuma@digitaltelkom.id`, bersuffix angka bila terpakai) yang tidak akan pernah identik dengan email akun Tania, sedangkan provisi INVITE memakai email asli sebagai UPN — dan pemilik produk mengonfirmasi ada pula populasi ketiga: akun korporat yang **sudah ada sebelum Tania**. Rantai (2) memakai kembali `UserRepository.FindByEmployeeID` yang sudah ada. Tanpa auto-create (NC-02) akun tetap dikelola Admin/provisi (FR-43–FR-46 spesifikasi 001). Kolom `entra_object_id` **sudah ada** (migrasi `0002`) dan bernilai NULL persis untuk keterkaitan "nol atau satu" yang diminta Key Entities — tidak perlu tabel baru (Technical I); indeks unik parsial ditambahkan agar satu `oid` tidak pernah memicu dua akun.
- **Alternatives considered**: **hanya** lewat work email seperti FR-004 semula (ditolak — inilah temuan R-6: akun hasil provisi CREATE tidak akan pernah cocok; pemilik produk menyetujui penggantiannya); hanya lewat `entra_provisions.object_id`/UPN (ditolak — memutus jalur email yang tetap dibutuhkan populasi akun korporat yang sudah ada sebelum Tania dan belum punya baris provisi); meminta Admin menyamakan email akun Tania dengan UPN hasil provisi (ditolak — UPN bersuffix angka tidak mungkin ditebak manusia, dan mengubah alamat masuk akun berisiko merusak jalur email + kata sandi yang wajib dijaga); membuat akun otomatis bila tidak ada (ditolak — NC-02 menolaknya tegas).

## R-6 — Masalah pada spec: UPN hasil provisi vs work email (diselesaikan dengan revisi FR-004, 2026-10-20)

- **Decision**: pemilik produk menyetujui **FR-004 jalur (a) langkah (2)** — memetakan lewat `entra_provisions.object_id` bila baris provisi ada — dan **spec telah direvisi** (2026-10-20; lihat baris `**Revisi**` pada `spec.md`). Implementasinya: **D5** langkah (1)–(3) dan **kontrak §3**.
- **Fakta kode (2026-10-20)**: `usecase/entra.go` memutus jalur provisi berdasarkan `isInvitedEmail` (hanya `telkom.co.id` → *invite*, UPN = email asli); selain itu → `buildUPN(fullName)` + `@digitaltelkom.id` (contoh: `Rina Kusuma Wardani` → `rina.kusuma@digitaltelkom.id`). `AccountService.Create` mengisi `users.email` dari input Admin, yang boleh berupa alamat kerja yang **berbeda** dari UPN turunan itu.
- **Dampak sebelum revisi**: untuk akun hasil provisi **CREATE**, klaim work email identitas korporat tidak identik dengan `users.email` → pemetaan FR-004 lama menolaknya, dan itu menurunkan peluang **SC-005** (≥80% masuk via SSO dalam 1 bulan).
- **Sisa yang bukan milik fitur ini**: baris provisi hasil **sinkronisasi** akun korporat yang sudah ada sebelum Tania hanya menolong bila mencatat `object_id`; bila tidak, akun itu tetap dapat masuk lewat langkah (3) selama email akun Tania = alamat masuknya. Pencatatan `object_id` saat sinkronisasi (dan kemungkinan nilai `action` ketiga pada CHECK migrasi `0008`) → `plan.md` **Open Item 6** (ranah Provisi Entra).

## R-7 — Di mana auto-redirect dijalankan dan bagaimana lingkaran pengalihan dihindari? (FR-001, FR-002)

- **Decision**: di **komponen login** (`src/app/(auth)/login/LoginForm.tsx`) — query `entraSsoStart` dipanggil saat mount; bila `enabled` **dan** mode normal **dan** tidak ada penanda fallback → `window.location.replace(authorizationUrl)`. Penanda `sessionStorage` `tania:sso:fallback` diset ketika pengguna memilih pintu email, atau kembali ke `/login` dengan `?sso=error|cancelled`; selama penanda ada → tampilkan form, **tanpa** redirect. Penanda dihapus setelah login sukses. **Opsi A** (disetujui pemilik produk 2026-10-20, D8) menambahkan dua hal: tautan "Masuk dengan email & kata sandi" **selalu terlihat** (bukan hanya setelah gagal), dan hasil "belum tertaut" diingat **7 hari** di `localStorage` `tania:sso:unlinked` sehingga kunjungan berikutnya langsung menampilkan form email.
- **Rationale**: `page.tsx` login sudah `dynamic(..., ssr:false)` (prerender tanpa endpoint GraphQL), jadi tempat yang alami untuk efek pengalihan adalah komponen klien. `state`/`nonce`/verifier **harus** hidup di client karena di generasi di sana; `window.location.replace` (bukan `assign`) menjaga `/login` tidak masuk riwayat sehingga tombol kembali tidak membawa user ke halaman yang langsung me-redirect lagi. Penanda pemutus lingkaran di `sessionStorage` — efeknya terbatas pada sesi tab; penanda "belum tertaut" di `localStorage` karena masalahnya bertahan berhari-hari sampai Admin memberi akses. Keduanya **petunjuk tampilan**, bukan penentu keputusan: server tetap yang menerima/menolak, dan keduanya dibersihkan begitu login berhasil di jalur mana pun.
- **Alternatives considered**: (a) server-side `302` dari halaman login — tidak ada di repo (frontend pure CSR untuk auth, tanpa handler server); (b) redirect di `src/proxy.ts` — ditolak: proxy tidak memanggil backend (komentarnya: "never the backend"), dan menambah panggilan GraphQL di middleware mengubah kontraknya; (c) auto-redirect **tanpa** penanda — ditolak: langsung melanggar FR-001 ("tanpa lingkaran pengalihan") saat pengguna memilih pintu email; (d) opsi B — dua pintu sejajar untuk pengunjung baru (ditolak pemilik produk 2026-10-20: pengguna yang punya akses kehilangan kenyamanan satu klik dan NC-03 "opsi utama" perlu ditinjau ulang); (e) opsi C — hanya penanda sesi tab seperti rencana awal (ditolak: pengguna tanpa akun korporat mengulang putaran gagal yang sama setiap hari).

## R-8 — Apa yang masuk ke kontrak GraphQL baru? (Contract-First)

- **Decision**: satu **query publik** `entraSsoStart(codeChallenge, state, nonce) → EntraSsoStart { enabled, authorizationUrl }` dan satu **mutation publik** `loginWithEntra(input: EntraLoginInput) → AuthPayload`; kontrak lengkap (input, kesalahan, kunci rate limit, payload audit) di `contracts/sso-entra.md` sebelum implementasi (D3, workflow Workflow item 1).
- **Rationale**: backend adalah satu-satunya pemegang `authority`/`clientId`/scope/`redirect_uri`, sehingga konfigurasi tenant tidak diduplikasi ke frontend (menghindari drift antar-repo); `enabled=false` membuat halaman login cukup tahu "jangan redirect" tanpa membedakan alasan. `authorizationUrl` memang bersifat publik di setiap alur OIDC, jadi mengembalikannya tidak membocorkan apa pun.
- **Alternatives considered**: konfigurasi via `NEXT_PUBLIC_ENTRA_*` (ditolak — duplikasi & drift); expose `entraSsoStart` sebagai mutation (ditolak — tidak ada efek samping, query cukup).

## R-9 — Rahasia, konfigurasi, dan kegagalan startup (FR-010, Prinsip IX)

- **Decision**: `ENTRA_REDIRECT_URI` bergabung dengan `ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET` (ketiganya **sudah ada** di `EntraConfig`); kredensial tetap hanya dari env/secret store. `APP_ENV=production` + `EntraConfig.Enabled()==false` → **gagal start**; di luar production → SSO dinonaktifkan + peringatan terstruktur (D7). Tidak ada nilai rahasia yang pernah masuk ke browser, URL, log, dokumen, issue, atau komentar.
- **Rationale**: SSO adalah jalur masuk utama menurut spec, sehingga kehilangan kredensial di production adalah kondisi yang harus terdeteksi saat deploy, bukan saat pengguna mencoba masuk (Prinsip IX). Di lokal, `make run` tanpa kredensial Entra tetap harus bisa menjalankan backend agar pengembangan halaman login & jalur fallback tidak terblokir — preseden persis sama dengan pola `EntraConfig.Enabled()` (provisi "not configured") dan `AIConfig.Enabled()` (chat) yang sudah diratifikasi.
- **Alternatives considered**: selalu gagal start tanpa kredensial (ditolak — menghambat pengembangan lokal tanpa manfaat keamanan; kredensial memang belum tentu ada di mesin dev); mengabaikan kondisi parsial (ditolak — sudah ditangani `ENTRA_*` "must be set together" di `validate()`).

## R-10 — Paritas sesi & audit (FR-007, FR-008, SC-004, SC-005)

- **Decision**: reuse `AuthService.issueSession` dengan parameter baru `authMethod` (D6); `Refresh` mewarisi metode dari token yang dirotasi; kolom baru `refresh_tokens.auth_method` (`local`/`entra_sso`). Audit SSO: `AuditLogin` dengan payload `{"method":"entra_sso","outcome":...,"reason":...}`; audit jalur lokal menambah `method:"local"` pada entry sukses (D10). SC-005 dihitung dari `audit_logs` (filter `action='LOGIN'`, kelompokkan `method`).
- **Rationale**: FR-008 dipenuhi *by construction* — masa berlaku, rotasi, deteksi reuse, denylist, dan penonaktifan akun memakai kode yang sama; SC-004/SC-005 butuh penanda yang konsisten di **kedua** jalur agar perbandingan masuk akal. Key Entities spec menyatakan sesi "kini mencatat metode masuk", jadi kolom sesi memang diminta spec, bukan penambahan spekulatif.
- **Alternatives considered**: menyimpan metode hanya di `audit_logs` (ditolak — tidak menutup Key Entities; perbaikan pada sesi menjadi tertutup audit setelah rotasi); kolom `auth_method` baru di `users` (ditolak — metode adalah properti **sesi**, bukan akun; akun yang sama bisa masuk dua cara).

## R-11 — Frontend: dependensi & penempatan (Technical V)

- **Decision**: PKCE dibuat sendiri dengan **Web Crypto** (`crypto.getRandomValues` untuk 32–64 byte verifier, `crypto.subtle.digest("SHA-256")` lalu `base64url`) + `state`/`nonce` via `crypto.randomUUID()`; state disimpan di `sessionStorage`; **tanpa `pnpm install` baru**. Lokasi: `src/features/auth/entra-pkce.ts` + halaman `src/app/(auth)/login/callback/page.tsx` + perubahan `LoginForm.tsx`.
- **Rationale**: Web Crypto tersedia di browser modern dan di Node ≥18 (jsdom untuk test), jadi satu implementasi dapat diuji di Vitest tanpa mock crypto. MSAL (`@azure/msal-browser`) adalah dependensi berat yang menghadirkan model token & cache miliknya sendiri padahal yang dibutuhkan hanya satu permintaan otorisasi + satu pemanggilan mutation; melanggar kendala pemilik produk ("tambahkan seperlunya") dan Technical V.
- **Alternatives considered**: `@azure/msal-browser` (ditolak — dependensi + model sesi kedua); library PKCE kecil (ditolak — ~30 baris Web Crypto sudah cukup).

## R-12 — Strategi pengujian

- **Decision**: backend memakai fake `EntraCodeExchanger` + `EntraIDTokenVerifier` untuk usecase (deterministik, tanpa jaringan), `httptest` khusus untuk parsing JWKS & verifikasi tanda tangan, baris baru `authz_test.go` (SSO tidak menambah hak akses), skenario `security_test.go` (pesan generik, tanpa rahasia di log), dan alur penuh `e2e_test.go` untuk `loginWithEntra` termasuk **rotasi refresh mewarisi `auth_method`**. Frontend memakai `MockedProvider` (pola `page.test.tsx` login & test modul fitur lain) untuk `/login` & `/login/callback`; Playwright untuk regresi jalur lokal (SC-003). Login **sungguhan** ke tenant hanya di UAT manual (`quickstart.md` §B) — CI tidak boleh bergantung pada kredensial tenant.
- **Rationale**: Technical III + determinisme; prinsip yang sama dipakai 005 (fake gateway, verifikasi provider di prasyarat).
- **Alternatives considered**: panggil endpoint Microsoft di CI (ditolak — butuh kredensial, tidak deterministik, kehilangan jaringan = merah).
